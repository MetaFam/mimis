I am working on a collaborative file system for public information,

The structure is stored in Janus Graph & the data in IPFS.

The structure modeled in the graph database is a copy-on-write unioned graph.

There are two separate graphs in the database with different root nodes:

* `Users`: off which there are `INCLUDES` edges, each of which has a unique `author` attribute containing an Ethereum address.
* `Write Layer`: which holds changes to the user's graph which haven't yet been serialized as updates.

The application will support two different modes, one for a single user and another for multiple users. In the single user scenario, the `Write Layer` will be the `Spot` at the base of their file system. For multiples, there will be a structure akin to the `Users` node where copy-on-write layers are stored in per-user graphs.

This allows single users to begin using the system without requiring setting up an Ethereum wallet.

Each `INCLUDES` edge connects to a `User` node which has a set of outgoing `USES` edges which have a `device` attribute containing a UUID and connecting to an `Update` node.

The data in the graph is stored as an immutable set of layered update graphs where each `Update` node has:

* a GUID for the device from which the update was published
* a link to the base `Spot` for that device's graph
* the paths to and any altered blobs or mounts contained in the update
* the CID of the most recent previous update from this device
* a sequence number identifying how many updates have been published from this device
* an Ethereum signature over the base CID, previous CID, sequence number, & device GUID

`Spot` nodes connect to other `Spot` nodes by `CONTAINS` edges with a `path` attribute representing an element in the path for resolving a resource.

`Spot` nodes also have a UUID that is set at the point of creation and stays the same across updates.

Each `Spot` can have `REPRESENTATION` edges, which have a `mimetype` attribute that must be unique for that `Spot`.

Each `REPRESENTATION` edge leads to `Blob` node which has a `cid` property with the IPFS content id of that blob.

When a `Blob` is being added, if there is already `Blob` for that mimetype for the given `Spot`, a `PREVIOUS` edge is made to the existing `Blob`.

In addition to `CONTAINS` edges, `Spot`s can have `MOUNT` edges that either connect to a `Spot` for references that should remain the same across updates, or they connect to a `Mount` node which has a `target` property with the UUID of the target `Spot`.

`MOUNT` edges have an optional `order` property, and they are searched in ascending `order` after any `CONTAINS` edges have been checked.

The contents displayed in the user's UI is generated by processing a set of `MOUNT` edges originating from the `Spot` `program → Mïmis → root`.

When `Spot`s or `Blob`s are removed, they are replaced with a `Tombstone` node in the copy-on-write layer which is then codified in an update.

So, the resolution process for a resource is:

1. Check the copy-on-write layer to see if it has the requested path by following `CONTAINS` edges.
2. Work backwards from the maximal completion of the path and traverse any `MOUNT` edges that exist in the copy-on-write layer in least first `order`ing.
3. Progress through the `MOUNT` edges in `MOUNTS` and repeat 1 & 2.
4. If the resource isn't found or if a `Tombstone` is the first node, return 404.

Also, a desired characteristic is for a user to be able to override files in another users tree for themself while maintaining the property that all updates for a given user are children of their `User` node. ¿Any suggestions on how to achieve this?
